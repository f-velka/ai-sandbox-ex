# AI エージェントサンドボックスの設計

## この環境が提供するもの

AI エージェントは、信頼できない指示やデータを処理しながら、ファイルの読み書き、コマンドの実行、外部サービスへの通信を行う。
エージェントに作業を任せるには、これらの操作が管理者の許可した範囲から出ないことを、エージェントの自制ではなく実行環境の構造で保証する必要がある。

この文書が設計を定めるのは、その実行環境を Dev Container として提供するサンドボックスである。
この提供物は三つの部品でできている。

- **サンドボックス本体**：エージェントを動かすコンテナ群。外向き通信は許可リストにあるホストだけへ中継され、永続的な書き込みは作業ディレクトリだけに残り、エージェントは管理権限を持たない。
- **検査コマンド `sandbox-check`**：この制限が実際に成立していることを、コンテナの内側から操作を試行して確かめる。
- **製品側の管理設定**：Claude Code と Codex が実行環境のネットワークを通らずに外部へ出る機能（Web 検索など）を無効化する。

設計は次の三つを優先する。

- **理解しやすい**：部品と概念を少なくし、各部品を一ファイルで読み切れる大きさに保つ。
- **始めやすい**：リポジトリを clone して Dev Container として開くだけで、既定の許可リストのまま動き始められる。
- **拡張しやすい**：変更したいことごとに、触るファイルが一つに定まる。

## 全体像

サンドボックスは、役割の異なる少数のコンテナを Docker Compose で組み合わせて作る。

```text
agent ── internal ネットワーク ── gateway ── egress ネットワーク ── インターネット
              │                               （許可リストのホストのみ）
             dns
（dind は agent のネットワークを共有する）
```

- **agent**：エージェントと利用者が作業するコンテナ。非 root ユーザーで動き、外部への経路を持たない内部ネットワークだけに接続する。
- **dns**：エージェントの名前解決をすべてゲートウェイへ向ける DNS サーバー。
- **gateway**：許可リストで外向き通信を制限する中継器。内部と外部の両方のネットワークに接続する唯一のコンテナ。
- **dind**（任意）：コンテナ内 Docker のエンジン。
- **policy/allowed-domains.conf**：許可する接続先の一覧。管理者がホスト側で編集する唯一のポリシーファイル。
- **sandbox-check**：agent 内に置く検査コマンド。

境界を実装するのは dns と gateway であり、agent には境界を実装する能力も外への経路も与えない。
境界がエージェントの外側にあるため、エージェントが agent コンテナ内で何を実行しても（子プロセス、コンテナ内 Docker のコンテナを含めて）、制限は同じに保たれる。

## 保証する性質

管理者、ホスト、境界を実装するコンテナ（dns、gateway）は信頼する。
エージェントは信頼できない指示やデータを処理し、agent コンテナ内で利用できる手段をすべて使い得るものとして扱う。

ファイルについて、次を保証する。

- 永続的な書き込み先は、作業ディレクトリ `/workspace` と、セッション保持用の名前付きボリューム（エージェント CLI の認証情報、利用者設定、キャッシュ）に限られる。
- 許可リストと製品の管理設定は、agent 内から変更できない。

通信について、次を保証する。

- 外向き通信は既定で拒否され、許可リストにあるホストへの HTTP と HTTPS だけが外部へ到達する。
- IP アドレスの直接指定、外部リゾルバへの名前解決、クラウドのメタデータサービスへの接続は到達しない。
- 稼働中の境界は、ホスト側での明示的な操作（gateway の再起動、リビルド）によってのみ変わる。

権限について、次を保証する。

- エージェントは非 root ユーザーで動作し、sudo と Linux capability を持たず、実行中の権限昇格（no-new-privileges）を禁止される。
- ホストの Docker やその他の管理機能へ到達できるソケット、デバイスを公開しない。

製品機能について、次を保証する。

- 実行環境のネットワークを通らない製品機能（Claude Code の WebSearch、Codex のライブ Web 検索、MCP サーバー）は、製品の管理設定で無効化または許可制になる。

これらの性質は、`sandbox-check` が agent の内側から観測して確かめられる。

## 保証しないこと

許可したホストへは、`/workspace` の内容を含む情報をエージェントが送信できる。
許可リストへの追加は、そのホストへの情報流出を受け入れることと同義である。

作業リポジトリはホストと共有され、この共有に伴う二つの経路は運用で防ぐ。
第一に、エージェントは書き込めない `.devcontainer/` の変更も、コミットとして履歴に含めることはできる。
その内容が境界へ効くのは人間が gateway の再起動またはリビルドを行ったときに限られるため、取り込み時のレビューで `.devcontainer/` への変更を確認することが境界を維持する前提になる。
第二に、ホスト側でこのリポジトリに対して行う git 操作は、エージェントが書き得る `.git` の内容（hooks、config）を信頼して実行される。
この経路を許容できない場合は、別のクリーンな clone から `git fetch` で取り込んで検分する。

Docker、Linux カーネル、エージェント製品自体の脆弱性による突破は防げない。
また、gateway と dns は境界を実装する信頼されたコンテナであり、その侵害はこの設計の保証の外にある。

監査基盤は含まない。
gateway が接続単位の決定ログ（後述）を残すため、記録の転送と保全は利用者が自分の基盤で行う。

## ネットワーク境界の仕組み

経路は二枚の Docker ネットワークで絞る。
**internal** は `internal: true` を指定した WAN への経路を持たないネットワークで、agent が接続する唯一のネットワークである。
**egress** は外部へ出られるネットワークで、gateway だけが接続する。
この構成では、agent からのパケットは宛先がどこであれ internal の中にしか届かないため、外部へ到達する唯一の方法は gateway に中継させることになる。
IP 直接指定、外部リゾルバ、メタデータサービスへの接続が到達しないのは、遮断ルールの結果ではなく、経路がそもそも存在しない結果である。

名前解決は dns コンテナで gateway へ集める。
dns は、A クエリに対して常に gateway の固定 IP を返し、それ以外のクエリには該当なしを返す（標準ライブラリだけの一ファイル実装）。
agent の DNS はこのコンテナに固定されるため、どの名前を引いても結果は gateway を指し、HTTP クライアントは設定なしで gateway へ接続する。

gateway は、接続先ホスト名を見て通すか遮断するかを決める。
HTTPS（443 番）では、TLS ハンドシェイクの先頭でクライアントが平文で送る **SNI**（Server Name Indication）から接続先ホスト名を読み取る。
HTTP（80 番）では、リクエストの Host ヘッダーを読む。
ホスト名が許可リストに一致すれば本来の接続先へ接続し、以後はバイト列を双方向にそのまま中継する。
ホスト名を読み取れない接続は遮断する（fail-closed）。

TLS は終端しない。
終端すると、中継器の CA 証明書を agent、コンテナ内 Docker、エージェントが起動するすべてのコンテナとビルドへ配布する必要が生じ、CA の秘密鍵が新たな保護対象になる。
終端しなければ、クライアントは接続先の本物の証明書を検証でき、WebSocket や gRPC も同じ中継で通り、配布すべき秘密がそもそも存在しない。
gateway は判定（許可リスト照合）と中継（バイト列の転送）だけを行い、HTTP の中身を解釈しないため、標準ライブラリだけの一ファイルに収まる。

遮断は、ポートによって次のように現れる。

- HTTP：理由文と `X-Sandbox-Blocked` ヘッダー付きの 403 応答。
- HTTPS：TLS アラート `unrecognized_name` を返して切断。

HTTPS の遮断が接続エラーとしてしか見えないことは、TLS を終端しないことの代償である。
そこで、遮断と障害の切り分けは `sandbox-check <host>`（許可リストとの照合と接続試行を併せて報告する）に持たせ、両製品が必ず読む管理配置（Claude Code の managed CLAUDE.md と Codex の `AGENTS.md`）にその案内を置く。

許可リストは、gateway が起動時に一度だけ読み込む。
ホスト側で編集した変更は、gateway の再起動（`docker compose -f .devcontainer/docker-compose.yml restart gateway`）で反映される。
稼働中の再読込をしないのは、許可リストが作業リポジトリのワークツリーにあり、その内容が管理者の編集だけでなくホスト側の git 操作（checkout、merge）でも変わるためである。
ファイルの変化を反映の合図にすると、エージェントが履歴に紛れ込ませた許可リストの変更が、人間がレビューする前に境界へ効いてしまう。
反映を明示的な再起動に限ることで、レビューが効力の前に挟まることを構造で保証する。

gateway は判定のたびに 1 行の JSON（時刻、ポート、ホスト、判定）を標準出力へ書く。
この**決定ログ**は `docker compose logs gateway` で読め、接続単位の監査記録として任意の基盤へ転送できる。

## ファイルと権限の境界

agent コンテナに見せるものを、マウントの列挙で最小に保つ。

- `/workspace`：作業対象。`.devcontainer` を含むプロジェクトのルートをマウントする。
- `/workspace/.devcontainer`：サンドボックス構成（許可リストを含む）の読み取り専用の重ねマウント。エージェントが環境起因の問題を自力診断できる読み取りビューを兼ねるため、`.devcontainer` には秘密を置かない。
- 名前付きボリューム：Claude Code と Codex の認証情報、利用者設定、セッションと、`~/.cache`（ビルドキャッシュ等）。コンテナを作り直しても保持され、`make reset` で破棄する。

権限は、非 root ユーザー、`cap_drop: ALL`、`no-new-privileges` で絞り、sudo はインストールしない。
seccomp だけは無効化する（`seccomp:unconfined`）。
Codex が Bubblewrap で自前の多層サンドボックスを作るには名前空間の作成が必要であり、境界は seccomp ではなく非 root、capability、マウント、ネットワークで維持する。

サンドボックス構成の配置は、三つの要求を同時に満たすように決めている。
構成をプロジェクトと同じリポジトリで版管理できること。
エージェントが稼働中の境界を変更できないこと。
変更の反映が管理者の明示的な操作だけで起きること。
一つ目は `.devcontainer` を作業対象のリポジトリに同居させることで満たす。
二つ目は読み取り専用の重ねマウントで満たす。これはエディタ、git、リダイレクトなどあらゆる書き込み経路に効き、マウントの解除や差し替えに必要な capability は agent に与えられない。
三つ目は、gateway が許可リストを起動時にしか読まないことで満たす（ネットワーク境界の章を参照）。
エージェントは `.devcontainer` の変更をコミットとして提案できるが、その内容が境界へ効くのは、人間がレビューを経て gateway の再起動またはリビルドを行ったときに限られる。
この重ねマウントの帰結として、`.devcontainer` 配下に差分がある版への git checkout は agent 内では失敗する。

## 検査コマンド sandbox-check

検査は宣言ではなく観測に基づく。
ポリシーファイルや compose の記述は期待値であり、実際の環境がそのとおりである証拠にはならない。
`sandbox-check` は、エージェントと同じ権限で禁止された操作を実際に試み、拒否されることを確かめる。

検査はこの参照構成を前提にする。
構成を前提にすると、観測の解釈を言い切れる。
たとえば「外部リゾルバへの問い合わせに応答がない」ことは、経路を持たない internal ネットワークの構成と合わせて、遮断の確認として解釈できる。

結果は検査項目ごとに三値をとる。

- **ok**：期待する状態を観測した。
- **ng**：境界の破れを観測した。
- **unknown**：観測を完了できなかった（ネットワークの一時的な失敗など）。

終了コードは、すべて ok なら 0、ng があれば 1、ng がなく unknown があれば 2 とする。

検査項目は次のとおりとする。

| 項目 | 観測 |
|---|---|
| `net.allowed` | 許可リスト先頭のホストへ HTTPS で到達する |
| `net.blocked-http` | 未許可ホストへの HTTP が 403 と `X-Sandbox-Blocked` で遮断される |
| `net.blocked-tls` | 未許可ホストへの TLS ハンドシェイクが失敗する |
| `net.dns-sinkhole` | 異なる外部名がすべて同じ IP（gateway）へ解決される |
| `net.outside-dns` | 外部リゾルバへの DNS 問い合わせに応答がない |
| `net.direct-ip` | 外部 IP アドレスへの直接接続が成立しない |
| `net.metadata` | メタデータサービス 169.254.169.254 へ到達しない |
| `fs.workspace-writable` | `/workspace` にファイルを作成できる |
| `fs.devcontainer-readonly` | サンドボックス構成 `/workspace/.devcontainer` と許可リストへ書き込めない |
| `fs.no-docker-socket` | ホストの Docker ソケットが存在しないか接続できない |
| `priv.non-root` | 実効ユーザーが root でない |
| `priv.no-sudo` | sudo で無人昇格できない |
| `priv.no-capabilities` | 実効 capability が空である |
| `priv.no-new-privileges` | no-new-privileges が有効である |

引数にホスト名を与えると、そのホスト一件の診断に切り替わる。
許可リストとの照合結果、一致したエントリ、接続試行の結果、接続先を追加する手順を表示する。
通信が失敗したとき、エージェントが遮断と障害を切り分けるための入口である。

Dev Container の起動時（postStartCommand）にも自動実行し、境界が壊れたまま作業が始まることを防ぐ。

## 製品側の管理設定

エージェント製品には、実行環境のネットワークを通らずに外部へ接続する機能がある。
Claude Code の WebSearch と Codex のライブ Web 検索は製品側のサーバーを経由し、MCP サーバーは任意の接続先を持ち込める。
これらはネットワーク境界では制限できないため、利用者設定より優先される管理配置の設定ファイルで無効化する。

- **Claude Code**：`/etc/claude-code/managed-settings.json`。`WebSearch` を拒否し、サンドボックスの通信先を管理ドメインに限定し、MCP サーバーを許可制（初期値は全拒否）にする。
- **Codex**：`/etc/codex/requirements.toml`。Web 検索モードを `disabled` と `cached` に限定し、MCP サーバーを許可制（初期値は全拒否）にする。

どちらも root 所有でイメージへ焼き込み、agent 内からは変更できない。
製品バージョンは agent の Dockerfile の `ARG` で固定する。
版を上げるときは、これらの設定キーが新しい版でも同じ意味で強制されることを製品の公式文書で確認してから `ARG` を書き換える。

## コンテナ内 Docker（dind）

エージェントに `docker` コマンド（build、run、compose）を使わせたい場合だけ、`.devcontainer/.env` に `COMPOSE_PROFILES=dind` を書いて dind サービスを有効にする。
既定で無効なのは、rootless Docker の追加要件（カーネル 5.11 以上、`/dev/net/tun`、非特権ユーザー名前空間）を、Docker を使わない利用者に課さないためである。

dind サービスは、rootless の dockerd を agent のネットワーク名前空間の中で動かす。
このため、エージェントが起動したコンテナとビルドの外向き通信と名前解決にも同じ境界がそのまま適用され、`-p` で公開したポートは agent の localhost に現れる。
TLS を終端しない設計により、内側のコンテナやビルドへ CA を配る必要もない。

dind は agent と同格の非信頼ゾーンとして扱う。
秘密（許可リストの実体、ホストの認証情報、ホストの Docker ソケット）をマウントせず、dockerd の待受は agent と共有するボリューム上の UNIX ソケットだけとし、TCP では待ち受けない。
cgroup の委譲がないため、`--memory` などのリソース制限フラグは効かない。

## リポジトリ構成

```text
.
├── README.md                     # 何であるか、始め方、設定
├── AGENTS.md                     # このリポジトリを改修するエージェント向けの原則(CLAUDE.mdが参照)
├── Makefile                      # up / down / reset / check / test / init
├── docs/design.md                # この文書
├── host-settings/                # コンテナを使えない利用者向けの管理設定(独立した提供物)
├── .devcontainer/
│   ├── devcontainer.json         # Dev Container 対応エディタ用の定義
│   ├── docker-compose.yml        # コンテナ群とネットワークの宣言
│   ├── bootstrap                 # .env の初期化（subnet とプロジェクト名の自動割当）
│   ├── policy/allowed-domains.conf
│   ├── certs/                    # 組織 CA（Zscaler 等）の任意投入場所
│   ├── agent/                    # agent イメージ: Dockerfile、管理設定、sandbox_check.py
│   ├── dns/                      # sinkhole_dns.py
│   ├── gateway/                  # sni_proxy.py
│   └── dind/                     # dind イメージ
└── tests/                        # 単体テストと統合テスト
```

bootstrap は、compose の subnet とプロジェクト名をプロジェクトのパスから決定的に導出して `.env` に書く。
同じマシンで複数のコピーを使ったときに、既定 subnet の取り合いで起動に失敗することを防ぐ。

組織のプロキシ（Zscaler 等）が外向き TLS を再署名する環境では、その CA 証明書を `certs/` に置く。
agent と dind のイメージがトラストストアへ取り込み、上流の TLS 検証を通せるようにする。

`host-settings/` は、コンテナを使えない利用者が製品の管理設定だけで制限を強制するための、この文書とは独立した提供物である。
保証の範囲と使い方は [host-settings/README.md](../host-settings/README.md) が定める。

## 拡張の指針

| やりたいこと | 触る場所 |
|---|---|
| 接続先を許可する | `policy/allowed-domains.conf` に 1 行追加し、gateway を再起動 |
| 言語ランタイムや CLI を足す | `agent/Dockerfile` に追記してリビルド |
| 別のプロジェクトで使う | そのプロジェクトのルートへ `make init` |
| コンテナ内 Docker を使う | `.env` に `COMPOSE_PROFILES=dind` |
| 決定ログを監査基盤へ送る | gateway コンテナの標準出力を Docker の logging driver で転送 |
| 内部サービスを足す | `docker-compose.yml` の internal へ固定 IP で追加し、IP で接続する |

## テストが固定する仕様

単体テストは、境界の判定ロジックを固定する。

- **gateway**：ClientHello からの SNI 抽出、Host ヘッダーの解釈、許可リストの書式と照合の意味論、ホスト名を読み取れない接続の拒否。
- **dns**：クエリの解釈と応答の組み立て、A 以外のクエリへの否定応答。
- **sandbox-check**：許可リスト照合が gateway と同じ意味論であること（同一のケース集合を両実装に適用して確かめる）。

統合テストは、実際のコンテナ群でこの設計が成立することを確かめる。
compose で起動し、`sandbox-check` が全項目 ok で終了すること、許可ホストへの到達、未許可ホストの遮断、許可リストの変更が gateway の再起動で反映されることを観測する。
